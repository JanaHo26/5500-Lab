# Lab 4 Steering Log

### Incident 1: Invalid resourceId on POST /reservations returns 500
- **Initial Agent Output:** Before starting Lab 4 I tested POST /reservations with `resourceId: "abc"` and got `500 Internal server error`. The server log said `Cast to ObjectId failed for value "abc" (type string) at path "_id" for model "Resource"`. When I asked the agent to build the new cancel endpoint, it added an ObjectId check for cancel, but it did not fix the same problem in POST, so POST still returned 500.
- **Root Cause:** `Resource.findById()` throws a Mongoose CastError when the id is not a valid ObjectId. That error is not a ValidationError, so the controller passed it to the centralized error handler, which always returns 500. The agent only fixed the code I asked about (cancel) and didn't go back to the older code that had the same issue.
- **Remediation Prompt:** "wait, at the start i tested POST /reservations with resourceId "abc" and it gave 500 Internal server error. the server log said Cast to ObjectId failed for value "abc". you fixed this for cancel but not for POST. POST should return 400 VALIDATION_ERROR when resourceId is not a valid id, because its bad input from the client. please fix it in the service the same way and test it on my server. i will restart the server after you edit, tell me when to restart. then commit, no co-authored-by line"
- **Resolution:** The agent added a `Types.ObjectId.isValid(resourceId)` check right before `Resource.findById` that throws a ValidationError. After restarting the server, POST with `"abc"` returned `400 VALIDATION_ERROR` instead of 500. I also checked that a valid but missing id still returns 400, reversed dates still return the date error, and an overlapping slot still returns 409.

### Incident 2: Tests ran against a stale server (false results)
- **Initial Agent Output:** While testing, the agent's curl requests hit my server on port 3000, which was still running old code because ts-node does not hot-reload. The first time, `?isAvailable=yes` returned 200, which made the new filter look broken. Another time, PATCH /cancel returned 404, which looked like the "not found" test passed, but it was actually Express's default HTML 404 because the route didn't exist yet on the running server. This happened 3 times.
- **Root Cause:** Code changes were saved to disk, but the running server was started before the edits. Both the agent and I were treating test results as valid without checking which version of the code was running.
- **Remediation Prompt:** "ok i restarted the server again, now it has your changes. you can test on port 3000. use my reservation 6ad6df6217c2d60e1db32fe4 to test cancel. after cancel, try to POST the same time slot again (resource 6ac46fd9a490e27557d4cd29, 2026-11-01 10:30 to 11:30) to check the slot is free now, its ok to add that one. also try /reservations/abc/cancel. if everything works then commit, no co-authored-by line"
- **Resolution:** The agent compared the server process start time with the file save time to prove when a test was stale, and refused to commit until tests passed on a server started after the edit. After a proper restart: cancel returned 200 with CANCELLED, cancelling again returned 200, `/reservations/abc/cancel` returned 404 JSON, the freed time slot could be booked again (201), and booking it a second time returned 409. I learned to always restart the server after the agent edits code and before trusting any test.
